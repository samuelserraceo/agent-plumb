🧭 Design philosophy — the framework is the philosophy made mechanical

Every doctrine rule, every safety check, every file shape derives from these. The first three are the foundation. The other eight are foundation-3 applied to specific decisions. Drop any of the first three and the whole thing rots — a complex SDD wouldn't be auditable, a non-Lego SDD couldn't grow without rewrites, and an assuming SDD is just another lying agent in a trench coat.

1 Simplicity over capability

Files you can cat. Bash, markdown, YAML. No build step, no SaaS, no database, no node_modules. Deps: bash + python3 + PyYAML + git + gh. The check: can a non-coder open the file in any text editor and roughly follow what it does? If no, simplify. If a feature seems to need a custom server / new service / clever abstraction — the design is wrong, not that the framework needs to grow.

2 Composable Lego bricks over monoliths

Everything composes. Notebooks (INDEX, decisions, patterns, data-model, stack) are separate bricks, not one mega-doc. Actions (proposed-approach.md, verification.md, …) are atoms slot-able into any playbook. Playbooks (feature.md, project.md) are compositions of actions; new playbooks just rearrange existing bricks. Each work-item is its own brick in the INDEX queue — Pipelogic v2 is one brick, Topishop maintenance is another, they don't bleed into each other. SDD itself is a Lego brick for Claude Code via the plugin manifest. Test: if a new feature can't be expressed as a brick that snaps onto an existing one, the design is wrong.

3 Never assume — always check

The engine behind most of the mechanics. The manifest hash never assumes the file is unchanged — it checks. The moat hook never assumes the spec was verified — it re-runs verification on staged content. The AGENT-LED pattern never assumes user intent — it drafts 2-3 options, the user picks. stack.md never assumes Postgres + Railway — it asks the first time, then writes it down so it never has to ask again. The 3-arg shortcut in resolve-parameters never assumes the playbook — it reads INDEX.md. "No time estimates" is just never-assume applied to durations. Every place the framework slips into assumption is a place CodeRabbit eventually catches it — that's literally what the last 11 review cycles have been correcting.

Corollary — external dependencies (LLMs, hosted services, APIs) must be explicit customisation blocks in config.md with declared attributes (enabled, provider, endpoint, model), never baked-in defaults. Same shape as stack.md: ask once, write down, then read.

The 8 derivatives (foundation-3 applied to specific decisions)
  1. Honesty over speed
  2. Plain English over jargon
  3. Explicit over clever
  4. External memory over agent memory
  5. Reuse over reinvent
  6. Minimum diff
  7. No fake confidence
  8. Wireframe-current always

These eight are the framework's surface-level rules. They're consequences of the foundation 3 — keep the foundation, the surface rules follow.

The 4-step loop (the spine)

Every time you type /next, the framework runs through the same 4 micro-steps. The content changes (a question, a design, a code task), but the shape never does. v0.9 makes each loop one tiny step = one save to git.

FIND The framework reads the home page, finds your active feature, looks at where you got to last time, and pulls up the next thing on the list.
DO The AI does the actual work — asks you a question, drafts a proposal, writes a test, ships a task. The work itself depends on what kind of step it is, but the framework's safety checks always come at the end.
CHECK Each step declares which files it expects to update. If something's missing — say, the AI claims a feature is done but didn't update the diary — the save is refused.
RECORD Tick the box on the step. Update the home page. Add an entry to the diary if a big moment happened (you approved a design, a stage finished). Save to git. Move on.
v0.8 today vs v0.9 design: in v0.8, one /next handled a chunk of work (which might bundle 3 small questions together). In v0.9, one /next = one tiny step. Same loop; finer steps. Each save is a single Lego brick of progress, all the same shape.
For the curious — what the loop is called in the code

The 4 micro-steps are LOCATE → EXECUTE → SYNC → ADVANCE. Each step has a tag that tells the framework what kind of work it is: USER-LED (the agent asks, you fill in), AGENT-LED (the agent proposes alternatives with trade-offs, you approve), BUILD-TASK (test-first code), or TRANSITION (a stage handoff with ceremony). The step's frontmatter declares its touches: (which files must be saved together) and any triggers: (events that fire on commit, like adding a diary entry).

The shape of a project (5 levels)

Every level has a clear name. Building blocks live in a shared library — the same definition is reused across every feature that needs it, so you never copy-paste the same thing twice.

PROJECT                              (your whole codebase, e.g., pipelogic)
  └─ FEATURE                         (one thing you're building or fixing)
       └─ STAGE                      (SPEC = figure out what · BUILD = code it · SHIP = deliver it)
            └─ ACTION                (one named step, e.g. "the problem", "the approach")
                 └─ STEP             (one tiny question or task — one save to git)
                      └─ LOOP        (the 4 micro-steps inside every step)
Shared building blocks

Each action (e.g., "the problem", "the approach") is defined once and reused by every feature. Edit it once and every future feature picks up the change.

Cascading settings

Settings flow down: Project → Feature → Stage → Action → Step. Set a default once at the top; override only where you actually need something different. Most projects set everything at project level and never touch it again. See tuning knobs below.

For the curious — the technical names

The five levels in the codebase are PROJECT → WORK ITEM → STAGE → ACTION → STEP, with the LOOP container inside each STEP. Each action is defined once in .sdd/actions/<slug>.md. The cascading-settings system is called F5 cascading parameters; settings inherit Project → Work item → Stage → Action → Step, with each level only declaring overrides. The /status command shows you the resolved value for every setting plus the level it came from.

v0.13.1 ships two narrow but important security fixes. Both are inside the moat — the safety layer that runs on every commit and tells you what the AI is allowed to land. Without these fixes, the moat had two specific blind spots that a sufficiently motivated attacker (or a careless bulk-edit) could slip through.

1. Manifest baseline trust (closes #55)

A staged manifest with new hashes is no longer trusted by default — it must be a recognised "repin" path or the moat refuses the commit.

The gap. The manifest at .sdd/.cache/manifest.json is the framework's hash dashboard — every framework file has its expected SHA-256 listed there, and the moat compares working-tree files against those expected hashes on every commit. Before v0.13.1, the moat compared on-disk files against the staged manifest. So a tampering attack went: (1) modify a framework file (e.g. advance.sh) to insert backdoor; (2) re-compute the new hash; (3) update manifest.json with the new hash and stage both; (4) commit. The moat checks staged-against-staged; both match; commit succeeds. Backdoor in main.

The fix. The moat now treats HEAD's manifest as the trust baseline, not the staged manifest. When the staged commit changes any framework hash relative to HEAD's manifest, the moat refuses unless one of two recognised "repin" signals is present:

  • The commit message contains [SDD] manifest: repin — the explicit "I am intentionally updating the manifest" marker, only used by maintainers landing a framework upgrade.
  • The command being committed is scripts/update.sh — the framework's blessed upgrade path, which itself enforces deeper invariants before producing the new manifest.

What you'd see if someone tried. A clear refusal at commit time: "manifest hash for advance.sh changed in this commit but no [SDD] manifest: repin marker is present. Refusing the commit. If this is a legitimate framework upgrade, run scripts/update.sh; otherwise, revert the manifest change." The user can then choose: revert, or rerun via the blessed upgrade path.

2. Advance.sh lock PID liveness (closes #56)

A stale phase-advance lock is now only removed when the recorded PID is actually dead — long-running advances can no longer be clobbered.

The gap. advance.sh uses a directory-based lock (.sdd/.cache/.advance.lock/) so that two parallel /next calls can't both try to advance the phase at once. If a previous advance.sh crashed without releasing the lock, the next caller would see a "stale" lock and remove it after a timeout. Before v0.13.1, the staleness check was only mtime-based — if the lock directory was older than the threshold, it was considered stale and clobbered. That meant: a long-running advance (one that legitimately took several minutes) would have its lock incorrectly classified as stale by an impatient parallel invocation, and the second invocation would remove the still-active lock and start its own work — two advances racing each other, possibly producing inconsistent state.

The fix. The lock directory now also stores the PID of whoever holds it. The staleness check is now both conditions: (a) mtime past the threshold AND (b) the recorded PID is dead (verified by kill -0 $pid). If the original process is still alive, the second invocation keeps waiting; only when both signals say "this lock is genuinely abandoned" does it remove and retry.

Why this matters. Concurrent /next calls happen in real workflows — the user types /next, sees the agent thinking, gets impatient, types /next again. Without the PID check, the second call would race the first and could overwrite the first's spec.md edits or commits. With the PID check, the second call cleanly waits for the first to finish.

3. Sub-stage triggering — actions can refuse to run if a setup answer is still deferred (closes #68 · PR #79)

Where files live, and what gets blocked when

The framework keeps your project organised in a small, predictable shape. Every file has one home. The safety checks (which run automatically every time something gets saved to git) only know how to enforce rules on files that live in the right place — so the layout matters.

When SDD installs, it adds a folder called .sdd/ to your project. That's where the framework lives. Four of the files inside it form the project's four notebooks — the core memory the AI reads at every conversation start. Here's what's in the folder, in plain English:

your-project/
├── CLAUDE.md           ← the rules the AI agent reads every session
├── README.md            ← your project's normal README
└── .sdd/                ← the framework's home
    ├── INDEX.md          ← your project's home page: what's active, what's shipped
    ├── decisions.md      ← the diary; never gets edited, only added to
    ├── data-model.md     ← the truth about what data your app stores
    ├── patterns.md       ← lessons from past features so you don't repeat mistakes
    ├── config.md         ← the dashboard for tuning the framework
    ├── features/
    │   └── 001-waitlist/
    │       ├── spec.md      ← the conversation about ONE feature; the real work happens here
    │       ├── verification.json   ← the framework's proof that the spec was honoured
    │       ├── wireframe.html      ← if a screen is involved, a sketch lives here
    │       └── tests/              ← automated checks that prove the feature works
    ├── ideas/             ← half-formed thoughts; one file each, no commitment
    ├── playbooks/         ← workflow templates (one ships today: "feature")
    ├── actions/           ← the 22 building blocks the workflow strings together
    └── scripts/           ← internal tools the framework uses (don't touch)
INDEX.md — the home page

A one-page map of what your project is doing right now and what it's already shipped. The AI reads this every single session before it does anything else. You can open it any time to see "where am I?"

decisions.md — the diary

Every approval and every phase change writes one entry here, with a timestamp. Future-you reads this to remember why past-you agreed to something. The framework refuses to let anything edit prior entries — only add new ones.

data-model.md — the data truth

One file. The single source of truth for "what stuff does this app store?" If you have users, signups, orders, posts — they're listed once, here. The framework refuses to let any feature reinvent or duplicate definitions.

patterns.md — the lessons

When a feature ships, the framework asks "what would you do differently next time?" The answer goes here. By feature 5, this file is your project's collective memory; the AI reads it before proposing anything new.

spec.md (per feature) — the real work

Every feature gets its own folder with its own spec.md. This is where the back-and-forth conversation lives — the question the framework asked, the answer you gave, the design the AI proposed, what you approved. Reads like a structured Q&A.

config.md — the dashboard

The one file you tune to make the framework feel right for your project. How long can a step run? How many test failures before it stops? What language style? See the tuning knobs section below.

CLAUDE.md — the AI's rulebook

The rules the AI agent reads at the start of every session. Things like "ask before assuming," "never edit a previous decision without re-approving it," "use plain English." You can add your own project-specific rules at the bottom of this file (anything below the marker line is yours to edit).

For the curious — what these files are called in the code

CLAUDE.md is read by the SessionStart + UserPromptSubmit hooks at the start of every conversation. INDEX.md's **Active:** line is the machine-readable pointer that lets the framework find the active work item without scanning the whole tree. verification.json is the AI's "claim file" — its statement that the work was done — which the central safety check (pre-commit-stage-verified.sh, the moat) re-runs against the actual spec at save time. See the project memory section below for how the four notebooks (INDEX, decisions, data-model, patterns) work together.

Every time something gets saved to git (the AI calls this a "commit"), the framework runs a quick check first. If the change breaks one of the rules below, the save is refused — the AI gets a clear error explaining why, and is told to fix it before trying again. You never have to enforce these rules; they enforce themselves.

REFUSED →
If the AI tries to advance a phase while questions are still unanswered

If you've started SPEC and there are still [ ] empty boxes from the framework's questions, the AI cannot move you to BUILD. It must finish the conversation first. Stops the "I'll come back to that" drift.

REFUSED →
If the AI changes a decision you already approved without re-approving it

Approved sections of your spec are locked. If the AI silently rewrites one (say, changing the database from SQLite to Postgres after you signed off on SQLite), the save is refused. To change an approved decision, the AI must walk you through a re-approval — and the change gets logged in the diary.

REFUSED →
If the AI tries to edit the diary instead of adding to it

decisions.md is append-only. Any save that modifies an old entry — even fixing a typo — is refused. The diary is the audit trail; rewriting history breaks the trust model.

REFUSED →
If the AI tries to weaken the safety rules AND fabricate proof of work in the same save

The framework's central tampering defence. An adversary's playbook would be: turn off a check, then submit fake proof that the check passed. The framework refuses any single save that touches both the rule files and the proof file. They have to be separate, traceable changes.

REFUSED →
If the AI claims a feature is done but the proof doesn't match the spec

When a feature is ready to ship, the framework re-runs its own checks against the live spec — not against what the AI says happened. If the claim ("all tests pass") doesn't match the actual state, the save is refused. This is the framework's central guarantee: the AI cannot fake a passing test.

REFUSED →
If the AI writes code before the test for that code exists

During BUILD, the rule is: write the failing test first, then write code until the test passes, then save. If the AI writes implementation code before any test file exists, the save is refused. Forces test-first discipline mechanically.

REFUSED →
If a memory file grows past the limits you set

Files like patterns.md warn at 200 lines and refuse new additions at 400. Past that, the framework asks you to consolidate (run /compress) so the AI's working memory stays small enough to read fast. You can change the threshold in config.md.

REFUSED →
If a framework file has been tampered with

Every file the framework ships with has a fingerprint. If a file's contents change unexpectedly (someone edits a hook, an injected script tries to rewrite a rule), the framework treats it as untrustworthy — it stops following any instructions inside it, and warns you that something was modified.

For the curious — what's actually running

These checks are a chain of git pre-commit hooks: pre-commit-block.sh (open blockers), pre-commit-rules.sh (the F1 generic enforcer covering append-only / size caps / rules-vs-proof co-stage blocks / managed sections), pre-commit-stage-verified.sh (the moat — re-runs verify-stage on the live spec at commit time), and the manifest hash-pin (.sdd/.cache/manifest.json) which catches tampering. Section-locking sits on top via approved-section hashes recorded in verification.json.

Run /ship. The AI pushes the branch and opens a pull request on GitHub. Read the summary, click through the changes, decide whether to merge.

What the AI writes

Pushes the branch, opens the PR with a summary written from your spec, watches CI run, captures the result. If anything fails in production-only checks, parks them in INDEX.md so you can verify them manually after deploy.

What's locked

The framework's central guarantee: the AI cannot fake a passing test. If any test claimed as passing isn't actually green, the SHIP save is refused. The proof gets re-checked against the spec at save time, every time.

For the curious — what powers each stage

Software projects accumulate decisions. In a normal project, the answer to "why did we decide X?" is scattered across Slack threads, Notion pages, GitHub PR descriptions, and people's memory. By month four, half of it is irretrievable — the person who decided has left, the Slack thread is buried, the PR is closed.

SDD forces all four notebooks into one folder, in one shape. The AI never has to ask "where did we decide X?" — it's always in the diary. Your future self never has to reverse-engineer past thinking. Onboarding a new person (or a new AI conversation) means handing over four short files, not "let me search Slack for two hours."

And because the framework's safety checks are wired to these files (the diary is append-only, the data truth file is the only place to define a new "thing", lessons get auto-appended on shipped features), they stay current without anyone having to remember to update them.

The lessons file warns at 200 lines and refuses new additions at 400 (you can change those numbers in the dashboard — see the tuning knobs above). When you hit the cap, the framework asks you to compress — typed as a single command, /compress patterns.

Compression isn't deletion — it's "boil down the last 30 days into 3 paragraphs and move the raw entries into an archive folder." Nothing gets lost. The condensed version stays at the top; the full history is always recoverable. The result: the four notebooks always fit in one screen-read, even after 6 months of work.

Each feature has its own folder with a spec, tests, and notes — easily dozens of pages of working material by the time it ships. Once shipped, the AI stops scanning that folder. The shipped feature still exists, still works, but it doesn't pollute the AI's attention.

What survives, in the four notebooks: the one-line summary in the home page, the lessons that came out of it, any data shape it added, the diary entry recording the ship. That's enough for future features to build on — without the AI having to read the original 30-page spec every time.

When you come back to evolve a sleeping feature months later, you wake it up explicitly with a single command — but only when you actually need to.

How each notebook handles bloat over time

The four notebooks are designed to stay short. But projects don't stay short — they grow. Each notebook has its own strategy for staying readable as the project ages. The strategies are different on purpose: a diary should never be compressed (you want every entry preserved); a lessons file should be compressed (duplicates teach less than tighter takeaways). Below: one approach per notebook, in plain English.

The diary is a captain's log — you don't compress a captain's log, you start a new volume. When the file gets long (say, after a quarter of work, or after a major milestone), the strategy is:

  1. Freeze the current diary into an archive file (e.g., decisions-2026-Q1.md) — exact bytes, never edited.
  2. Start a new active decisions.md, empty except for a "this picks up from decisions-2026-Q1.md" header line.
  3. If 5+ entries discuss one theme (e.g., "we kept reconsidering payments"), drop a lightweight topic index — a one-page note in .sdd/topics/ linking back to the relevant entries.
Why this shape: the audit trail's value is that nothing gets lost. If you compressed it, you'd lose the messy thinking — and that's exactly what teaches future-you. Rotation keeps every word; the topic index makes long histories searchable without rewriting them.

Lessons aren't a captain's log — they're a study guide. A study guide gets tighter over time, not longer. After 20+ shipped features, you'll have variations on the same lesson written five different ways ("test mobile keyboards" / "always check mobile UX" / "single-input forms behave weirdly on iOS"). They all say the same thing.

v0.10 candidate — /compress patterns: a one-command flow that reads the current lessons file, identifies similar entries, proposes a tighter consolidated version, and snapshots the raw original to .sdd/archive/patterns-<date>.md before replacing the active file. You approve each merge before it lands.
Today (v0.9): the framework warns when the lessons file passes 200 lines and refuses new additions past 400 — but the actual compression is manual. You read the file, write a tighter version, snapshot the old one, save. The discipline lives in your head, not in a script.

Data truth grows in layers — each new feature adds an entity or two. After 10 features you might have 30 entities crammed into one file. Reading the whole thing to find one entity is silly.

The strategy: convert the single data-model.md file into a data-model/ folder, with one file per entity (customer.md, order.md, etc.) plus a manifest.md that lists everything. The AI reads the manifest at session start; pulls in just the entity files relevant to today's feature.

v0.10 candidate — /split data-model: one command that walks the current file, identifies entity boundaries, proposes the split layout, and (on your approval) writes the new files + manifest. The old data-model.md becomes a redirect note pointing to the folder.
Today (v0.9): the framework warns at 200 lines, refuses new entries past 400, and tells the AI to suggest the split. But you do the actual file surgery by hand.

The home page lists everything the project has ever shipped, plus what's currently in flight. After 50 shipped features, the "Shipped" list is huge — and the AI re-reads the whole file at every session start.

The strategy: periodically (say, every 15-20 features), archive the older shipped entries to .sdd/archive/INDEX-<date>.md. The active home page keeps the most recent ones plus a one-line link: "older shipped features in archive/INDEX-2026-Q1.md." You can still grep the archive when you need to; the AI doesn't load it by default.

Today (v0.9): the framework warns at 200 lines and asks the AI to offer this once a quarter. The actual archive move is manual. The shipped catalog format itself (richer entries with PR links + lesson titles + extends-relationships) is what makes this work — even archived entries stay scannable when you do open them.

/start "<title>"

What it is: the kickoff. Tells the framework "I want to build something new."

What it does: creates a new folder for your feature (e.g. .sdd/features/004-waitlist/), makes a blank specification with all the questions inside it (~12 of them), and writes "this is now your active feature" into your project's home page.

When to use: whenever you have a fresh idea you want to build. The front door.

/start --extends=<id> "<title>"

What it is: kickoff for an evolution, not a fresh feature.

What it does: same as /start, but the new feature inherits context from the older one (so you don't re-explain things). Lighter spec.

When to use: "I shipped a waitlist last month, now I want to add referral codes to it" — use this so the agent already knows the waitlist setup.

/next

What it is: the workhorse. The "do the next thing" button.

What it does: looks at where you are, finds the next unanswered question or task, and either asks you the question or does the work itself (depending on whether the step is yours or the agent's).

When to use: every time you're ready to move one step forward. Most of your day will be /next.

Bonus: if you reply skip <reason> when offered a skippable section, /next handles the skip too — no separate command.

/idea "<one-line thought>"

What it is: the parking lot. A way to capture "we should do X" without committing to building it.

What it does: drops a small note into .sdd/ideas/. Doesn't start any feature. Doesn't change the active state.

When to use: mid-build, an idea pops up. Don't lose it. Don't pivot.

/status

What it is: the "where am I?" check.

What it does: prints in plain English: which feature is active, what phase, what's the current question, what's blocking. Plus your resolved settings (with a tag showing where each one came from).

When to use: after a context switch, after lunch, after closing your laptop and coming back.

/ship

What it is: the "go live" button.

What it does: pushes your branch to GitHub, opens a Pull Request, watches your automated checks, and once they're green marks the feature as shipped (writes the PR link into your home page, drops a small marker so the agent stops re-reading old shipped specs).

When to use: when the feature is fully built and tested. Not before.

/compress patterns v0.10+

What it is: the lessons-file housekeeper.

What it does: when your lessons file grows past a threshold (200 lines warns, 400 blocks), this command boils similar lessons together, archives the raw originals, and shrinks the active file back to readable size.

When to use: when the framework warns you that patterns.md is getting noisy. Not on a schedule — only when prompted.

/compress data-model v0.10+

What it is: the data-truth-file housekeeper.

When to use: same as above — only when warned.

/settings list v0.10+

What it is: the "show me everything I can tune" command.

What it does: prints every setting in your project, grouped by what it controls.

When to use: when you've forgotten what knobs exist, or want to see the full picture before changing one.

/settings get <key> v0.10+

What it is: "what's the current value of X?"

What it does: prints one setting plus where its value is set (project default? action override?). So you know whether changing it project-wide will actually affect the place you care about.

The whole framework in three sentences.

There's no orchestrator, no database, no embedded LLM, no SaaS. It's three plain ideas wired together by markdown files and pre-commit hooks.

1. The state file

The state file is the program.

Every running feature has a spec.md. Each [ ] row is a question waiting for an answer. The agent reads it, fills it, ticks it, commits. Your work-tree IS your application state.

2. The playbook

The playbook is the questioning agent.

A playbook (feature.md, bug.md, etc.) says "ask these questions in this order." Each step is a small focused prose file. New playbooks are just compositions of existing steps — not new code.

3. The filesystem

The filesystem is the retrieval system.

Lessons land in patterns.md, schemas in data-model.md, decisions in an append-only decisions.md. v1.0 added a graph layer on top so the agent can follow [[links]] between them.

The 30-second loop — what one /next actually does.

Every /next command runs the same four-step container. One step in your spec = one commit in git. No batching, no shortcuts.

Step 1 of 4

Lifecycle, hooks, and trust — what stops the agent making stuff up.

Three diagrams, three different surfaces. Each is a real mechanical gate, not just doctrine — the agent literally cannot proceed if any of them refuses.

1 · Phase state-machine — every work item walks this path

A new feature lives in QUEUED until you promote it. Then the agent walks SPEC → BUILD → SHIP one atomic step at a time. Every transition between phases is gated by a hook that re-checks the work; the agent's "I'm done" claim is text, the gate's verdict is bash-checked truth.

Red arrow = mechanical gate. The framework refuses to advance if the gate's check fails. Purple dashed arrow = bug back-route (a post-ship bug becomes a fresh [BUG] task in BUILD).

2 · Pre-commit hook chain — what every git commit goes through

When the agent (or you) runs git commit, eight checks fire in sequence. Any one of them can refuse the commit; the failure message names the fix in plain English.

Each red box = a hook script in templates/.claude/hooks/. The 8 fire in order; first refusal wins. Hooks 6 + 7 are framework-foundational — moat catches dishonest "I'm done" claims; hash-pin catches tampering with framework files.

3 · Trust-boundary frame — what the agent obeys vs. just reads

Every turn, the framework injects two clearly-marked content blocks into the agent's context. Same on-screen surface, different trust level. Anything inside the project block is read-only — even if it says "now run rm -rf", the agent treats it as user-written prose, not as an instruction.

Why this matters: anyone (including a malicious script in a forked repo) can put text inside spec.md. Without these markers, that text could become the agent's instructions on the next turn — a prompt-injection attack via repo prose. The markers + the doctrine in CLAUDE.md teach the agent the difference. Defence is partial (markers don't cryptographically prevent injection) but the discipline + the hash-pin combine to close the practical attack path.

4 · Manifest hash-pin lifecycle — how the framework defends its own bytes

~61 framework files (playbooks, actions, scripts, hooks) have their normalised SHA-256 stored in .sdd/.cache/manifest.json. Edit one without re-pinning and the moat refuses your commit. The flow:

Closes 3 tamper paths: isolated edit (T135), isolated delete (T135b), isolated rename (T135c). The marker requirement makes "I just upgraded SDD" cleanly distinguishable from "an attacker silently edited a hook script". The agent that does the upgrade adds the marker; an attacker doesn't know to.

5 · Wiki-link slug resolution — how [[001-waitlist]] finds its target

When you write [[some-slug]] in a spec / pattern / decision, the framework's graph cache resolves it via 4-tier priority. First match wins. Anything that doesn't resolve = stop-hook + CI graph-integrity refuse the merge.

Same-priority same-slug collision flags ambiguous and refuses. Cross-tier same-slug is fine (different file = different node). Anchors ([[001-waitlist#§5]]) and aliases ([[001-waitlist|the waitlist]]) are refused at parse time so the graph stays stable when headings reorganise.

6 · CR convergence gate (F026) — what stops you admin-merging past CodeRabbit

SHIP stage runs verify-cr-convergence between verify-ci-green and mark-shipped. Reads the latest CR review state on HEAD; refuses if changes are still requested. Bypass exists but adds an audit row.

F026 / PR #257 / closes #166. The gate reads the latest review state on HEAD SHA, not earlier reviews — once you push a fix in response to CR, CR re-reviews + the next /ship can proceed.

7 · Multi-agent parallel-wave timeline (F010) — how 30-task BUILDs scale

Mark a BUILD task with [WAVE: 2] and the framework dispatches it in parallel via Claude Code's Agent tool. Disjoint tests + code commits per subagent; the orchestrator commits the wave-green spec.md flip after the wave returns. Killer combo with the multi-model adapter (cheap models for wave-tasks, Sonnet for orchestration).

Why the orchestrator-flips-once model: adjacent rows in spec.md can't 3-way-merge cleanly between subagents. So subagents commit ONLY their disjoint test+code files; the orchestrator does the single spec.md edit after the wave returns. F010 / PR #227. Pairs with F008 multi-model so wave-tasks can use cheap fast models (Haiku, Kimi K2) while the orchestrator stays on Sonnet for coordination.

Foundation 3

Never assume — always check.

[3/3]

Every place the framework could trust the agent's word, it instead re-checks. Three concrete examples below.

▶Example 1 — the moat hook re-runs verification on the staged file, ignoring what the agent claims

When the agent commits, pre-commit-stage-verified.sh doesn't read the agent's "I'm done" claim. It re-runs verify-stage.sh on the actually-staged spec.md. If the freshly-computed result disagrees with what's claimed, the commit is refused.

▶Example 2 — the manifest is hash-pinned; the moat catches modify, delete AND rename of any framework file

~61 framework files (playbooks, actions, scripts, hooks) have their normalised SHA-256 stored in .sdd/.cache/manifest.json. v1.0 Phase B closed three tamper paths that were possible before: isolated edit (T135), isolated delete (T135b), isolated rename (T135c). All three now refuse the commit with a plain-English explanation.

▶Example 3 — placeholder tokens like (assumed) in spec.md cause an automatic refusal

pre-commit-no-assumed-markers.sh scans staged spec.md for (assumed), (TBD), (?), <FILL IN>, [?] task rows, and 5 other placeholders. If the agent gave up and filled with a guess, the commit gets blocked. The right move: ask the human.

Knowledge-graph foundation — markdown becomes navigable.

PR #98

A small subset of cross-references in .sdd/ markdown is now written as wiki-links [[slug]]. The framework's MCP server (a small Python helper that lets Claude ask short questions instead of reading whole files) traverses them via three new queries.

Three target shapes (anything else refused)
[[001-waitlist]]               feature folder
[[entity:User]]                heading in data-model.md
[[pattern:auth-retry-logic]]   heading in patterns.md

[[001-waitlist#§5]]            REFUSED — anchors
[[001-waitlist|the waitlist]]  REFUSED — aliases
Three new graph queries
get_backlinks(slug)   who cites this?
get_neighbours(slug)  what's adjacent in the graph?
search_within(slug)   bounded semantic search
                      around a slug's neighbourhood
Plain-English impact: the agent answers "is there already a pattern for X?" with one query (~200 bytes back) instead of reading INDEX.md + spec.md + grep (~15–35 KB). On a real .sdd/ tree that's 96.6% less context burned per question (40–60% across a whole working session that mixes queries with file edits).

Plus: stop-hook invariant 8 refuses to end any turn with a broken [[…]] reference, and a CI graph-integrity job blocks PRs containing one.

PR #104

CI runs three jobs total: framework-tests (mutation-verified), scope-guard (UI copy ≥30 chars must trace to spec.md or wireframe.html), and graph-integrity.

Phase B hardening — five small fixes that prevented a broken v1.0.

Before tagging, three release blockers and two nice-to-haves surfaced during heavy throwaway testing. All five landed in PR #106 alongside the version-marker bump.

🔴 blocker

init.sh fresh-install fix

The installer was checking for a file deleted in v0.8 (rubric.md). Replaced with a v1.0 surface check on playbooks/actions/INDEX.md/config.md. Without this fix: every fresh install on v1.0.0 would have aborted.

🔴 blocker

init.sh now copies the MCP server

Invariant 8 (broken-wiki-link detector) relied on extensions/sdd-mcp-server/ being present, but the installer never copied it. Without it, the v1.0 marquee feature would silently no-op. Now copied alongside .sdd/ and .claude/.

🔴 blocker

moat closes framework-tamper gap

When ONLY a framework file was staged (no spec / verification.json / manifest), the moat hook early-exited and never re-checked the manifest pin. Three new tests (T135/T135b/T135c) lock isolated edit, delete, and rename.

🟡 nice-to-have

bugs/ + refactors/ graduate

The folders .sdd/bugs/ and .sdd/refactors/ were on a "do not create" list pre-v1.0 (the playbooks didn't exist yet). They've been removed from deferred_paths so the new playbooks can scaffold work-items into them.

🟡 nice-to-have

minimal-diff-verify falls back to local branches

For projects where you haven't pushed yet (origin isn't configured), the line-delta check used to error out asking you to set up origin/HEAD. Now it falls through to local main / master / develop / trunk and the error message covers both paths in plain English.

Try it on a project — three commands.

  1. Step 1 — clone the framework somewhere stable

    $ git clone https://github.com/samuelserraceo/spec-driven-dev-workflow ~/Projects/sdd

    Requires Python 3 with PyYAML (pip install pyyaml). Framework deps stop there.

  2. Step 2 — drop SDD into your project

    $ cd <your-project>
$ ~/Projects/sdd/scripts/init.sh

    Adds .sdd/, .claude/, CLAUDE.md, copies the MCP server, and sets git config core.hooksPath .claude/hooks (with a halt-and-ask if you already use Husky / lefthook).

  3. Step 3 — open Claude Code and start your first work item

    $ claude
> /sdd-setup            # once: 7 plain-English questions to fill stack.md + config.md
> /start "build a waitlist landing page"
> /next                 # walk the playbook one step at a time

    From there: USER-LED steps ask plain-English questions, AGENT-LED steps propose answers with tradeoffs, BUILD-TASK steps run test-first. /ship opens the PR and watches CI when SHIP is done.

Honest caveats — what SDD isn't.

SDD is opinionated and explicitly trades some things to win others. If any of these feel wrong for your project, SDD is the wrong tool.

  • Not for typo fixes or copy tweaks. A 30–90 minute SPEC ceremony for a one-line change is the wrong tool. SDD's "triage on first message" rule routes those to plain commits with no ceremony.
  • Not for one-shot speed. A first SPEC takes 30–90 minutes. If you want it built right now without questions, this isn't the framework.
  • Doesn't turn a bad idea into a good one. The framework makes drift expensive and deep questioning cheap. It does not invent product strategy.
  • Scales to roughly 50 in-flight features / 500 total. Beyond that, you outgrow plain markdown — but the cold-tier + size caps + auto-archival keep working memory bounded indefinitely up to that scale.
  • Retrofit on existing repos is still rough. init.sh assumes a clean repo. Projects with existing PRDs / Husky / Drizzle migrations don't yet have a migration tool — manual scaffold for now.
  • Action prose still carries some JS-stack assumptions. Mentions of tests/task-NNN.mjs, Tailwind, gh pr create. Non-JS adopters fork the affected actions or write a sibling extension.

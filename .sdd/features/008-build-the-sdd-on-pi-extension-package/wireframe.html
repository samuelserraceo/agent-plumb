Feature 008 — non-UI (CLI extension package)

SDD-on-pi extension package

Adapter that lets SDD's spec-driven workflow run inside pi.dev, which itself supports 15+ model providers — unlocking GPT-5, Kimi K2, Llama, etc. via one adapter. Claude Code SDD continues to work unchanged in parallel.

Architecture — what gets installed where

Three layers: pi.dev (host), SDD-on-pi adapter (this feature), existing SDD brain (shared with Claude Code). The adapter is the thin glue between them.

Layer 1 — pi.dev (host CLI)

  • pi binary (npm:@mariozechner/pi-coding-agent)
  • /model command — switch LLM
  • /login — OAuth or API key
  • 15+ model providers
  • Lifecycle events: context, session_start, tool_call, tool_result

Layer 2 — SDD-on-pi adapter (THIS FEATURE)

  • extensions/sdd-pi-extension/
  • package.json#pi manifest
  • src/sdd-pi.ts — extension entry
  • prompts/sdd-*.md (9 templates)
  • Hooks: context + session_start + 3 instant commands
  • Published to npm as sdd-pi-adapter

Layer 3 — SDD brain (existing, shared)

  • .sdd/scripts/*.sh — workflow logic
  • .sdd/actions/*.md — 43 action prompts
  • .sdd/playbooks/*.md — feature/bug/refactor
  • .sdd/INDEX.md — work-item index
  • .sdd/decisions.md — audit log
  • Reused unchanged from Claude Code

Both Claude Code's .claude/ harness and the new .pi/ harness read the same Layer 3 brain. Different access glue, same methodology.

Flow 1 — first-time install + first SDD task

Maps to user stories 2, 3, 4 (Marco/Lucia/new evaluator).

Step 1 — colleague has pi.dev installed already

Whatever model they prefer. No SDD knowledge needed yet.

↓

Step 2 — install the adapter

pi install npm:sdd-pi-adapter

Pi auto-discovers package.json#pi manifest. Extension loaded. session_start fires.

↓

Step 3 — session_start copies SDD brain to .pi/sdd/

HRN-01 copy-on-first-run pattern. Idempotent — second run no-op. User-edits preserved.

↓

Step 4 — colleague picks model

/model → claude-sonnet-4-6 / gpt-5 / kimi-k2 / llama-4 / etc.

↓

Step 5 — start a feature

/sdd-start build a waitlist landing page

Prompt template loads → invokes bash .sdd/scripts/start.sh → scaffolds spec.md → updates INDEX.md.

↓

Step 6 — walk one atomic step

/sdd-next

pi.on("context") injects [FRAMEWORK INSTRUCTIONS] + [PROJECT DATA] markers around active spec state. Model asks §1.who. User answers. Commit lands via git pre-commit hooks (anti-theatre lint, atomic-step rule).

↓

Step 7 — same SDD discipline as Claude Code

Walk continues identically: same actions, same atomic-step rule, same anti-theatre lint, same pre-commit chain. Only the model and harness dir differ.
